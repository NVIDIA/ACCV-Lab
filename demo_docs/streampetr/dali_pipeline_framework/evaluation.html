Evaluation

This page summarizes the performance impact of using the DALI Pipeline Framework as a replacement for a conventional PyTorch Dataset + DataLoader when training StreamPETR on NuScenes mini. It also describes a separate data-loading-only evaluation, which measures data-loader iteration time without model training.

See also

For the pipeline and integration changes behind these results, see the DALI Pipeline Framework demo and its data-loader integration tutorial. The Optimization Testing Tools demo explains the runtime measurements and profiling support used in the evaluation.

Training Experiment Setup

Configuration

The training is performed for the NuScenes mini dataset, using the StreamPETR model. In order to evaluate a realistic setup with a high pre-processing overhead, we increase both the image resolution and the batch size compared to the original configuration. We use the following configuration:

  • Image size: 1024 × 372

  • Batch size: 8 per GPU

The training evaluation was performed with the standard PyTorch data loader and the data loader built with the DALI Pipeline Framework on 2 and 8 GPUs. The model implementation is fixed within each comparison.

Data

  • NuScenes mini

  • The mini training split is too small to populate ordinary sharded sampling with 8 GPUs and a batch size of 8 per GPU. For these evaluations, each GPU therefore samples the whole dataset instead of a separate shard. The DALI Pipeline Framework comparison and profiling configurations enable this behavior for both loaders by setting data_loading_config.replicate_dataset_per_gpu=True. This is a custom option added to the demo for these evaluations, not a standard NVIDIA DALI or StreamPETR configuration option.

Important

Replication allows performance measurements with a small dataset. Each GPU sees the same sample order within a run. The underlying NVIDIA DALI pipeline derives its reproducible augmentation seed from the sampling rank, so the provided configurations also use identical augmentations across GPUs. PyTorch worker seeds use the real rank, so its augmentations can differ across GPUs. Sample order is not guaranteed to match between the PyTorch and DALI Pipeline Framework variants.

DDP, GPU assignment, and validation sharding are unchanged. These runs measure a replicated workload; they do not represent training on independent batches across GPUs. Disable the option for normal sharded training with enough data. With one GPU, the option does not change sampling. See the data-loader integration tutorial for the implementation.

Adaptation to the DALI Pipeline Framework

  • Replace the PyTorch DataLoader by a DALI pipeline

  • Code changes are limited to the pipeline setup vs. PyTorch Dataset and DataLoader

  • The training loop implementation remains unchanged

Discussion

The results show that the DALI Pipeline Framework leads to a speedup of × 1.13 for the 2-GPU configuration and × 1.22 for the 8-GPU configuration, with the speedup being larger for the 8-GPU configuration. The CPU usage is reduced by around 57% in both configurations. Note that for both the DALI Pipeline Framework and the reference implementation, the runtime increases for the 8-GPU configuration compared to the 2-GPU configuration. However, the increase is much smaller for the framework-backed pipeline, indicating that while the CPU is not fully utilized in the reference approach, there are already bottlenecks present which can be overcome by the framework-backed pipeline.

Data Loading Only

This experiment compares the PyTorch data loader and the data loader built with the DALI Pipeline Framework without running model forward or backward passes or optimizer steps. The DataPipelineRuntimeEvalRunner repeatedly fetches the next batch, measuring data loading and preprocessing separately from model training. Pipeline construction is outside the timed loop.

Both use NuScenes mini, one GPU, a batch size of 8, and an output image size of 1024 × 372, matching the per-GPU batch size and preprocessing settings of the training experiments above. Random augmentations are enabled. The PyTorch reference uses eight DataLoader worker subprocesses (workers_per_gpu=8); it does not use a single worker. The DALI Pipeline Framework variant replaces the PyTorch DataLoader and uses one external-source Python worker (py_num_workers=1) plus four NVIDIA DALI CPU/mixed-operator threads (num_threads=4).

Each run fetches 1,000 batches, excluding the first 300 as warm-up and averaging the runtime over the remaining 700 batches. The runner prints Average runtime in seconds per batch; multiply by 1,000 to report milliseconds below.

Unlike the 2-GPU and 8-GPU training experiments, this comparison uses a single GPU and performs no model training. Report its runtimes separately from the training runtimes.

Important

This experiment is measuring the data-loading performance in isolation. It is not a prediction of training speedup. During training, this work overlaps with the model computations, so faster data loading does not translate directly into an equivalent reduction in training time.

The benefit during training depends on the available CPU and GPU resources and how they are shared. For example, increasing the number of workers per GPU can help keep the GPU supplied with data, but too many workers across GPUs can compete for CPU resources and slow data loading. Use experiments with the full training pipeline to assess the benefit for a particular use case (such as the experiment described above).

How to Run

Note

This section assumes that you are running the evaluation in the Docker container set up as described in the StreamPETR Docker setup, with the StreamPETR implementation located at /streampetr. Configuration paths below are relative to demos/streampetr/projects/configs/StreamPETR/.

Running the Evaluated Training Variants

The training evaluation used the following standard configuration pairs. Within each pair, the model implementation is fixed and only the data loader changes.

Run the configurations individually with the distributed training helper dist_train.sh. For this demo, the helper was modified to pass --no-validate to train.py and optionally launch training under nsys profile. It takes the configuration path and GPU count as its first two arguments:

cd /streampetr/tools

# 2-GPU comparison
bash dist_train.sh /streampetr/projects/configs/StreamPETR/Evals/dali_ref_2_gpu.py 2
bash dist_train.sh /streampetr/projects/configs/StreamPETR/Evals/dali_test_2_gpu.py 2

# 8-GPU comparison
bash dist_train.sh /streampetr/projects/configs/StreamPETR/Evals/dali_ref_8_gpu.py 8
bash dist_train.sh /streampetr/projects/configs/StreamPETR/Evals/dali_test_8_gpu.py 8

Alternatively, run all four evaluated training configurations and save their logs with:

cd /streampetr/tools
bash run_dali_eval.sh

The demos/streampetr/tools/run_dali_eval.sh script stores the results in the res_dali_eval folder in the current working directory.

Note

The GPU-specific configuration files inherit their settings from Evals/_base_/, which builds on the shared training configuration in _Base/base.py. The image size used by this evaluation (1024 × 372, as described in Training Experiment Setup) is set in _Base/dali_larger_images.py. The configurations in Evals/_base_/ select the data loader and whether to enable the Batching Helpers optimizations, and enable replicated sampling. The launch command determines the actual GPU count; run_all_evaluations.sh discovers the GPU-specific configurations and derives their GPU counts from the filenames.

Running the Evaluated Data-Loading-Only Variants

The separate data-loading-only results use DALILoadOnly/ref_load_only.py for the PyTorch reference and DALILoadOnly/dali_load_only.py for the DALI Pipeline Framework variant. Run them individually with:

cd /streampetr/tools

python train.py /streampetr/projects/configs/StreamPETR/DALILoadOnly/ref_load_only.py --no-validate
python train.py /streampetr/projects/configs/StreamPETR/DALILoadOnly/dali_load_only.py --no-validate

Alternatively, run both configurations and save their stdout and stderr logs with:

cd /streampetr/tools
bash run_dali_load_only.sh

The script writes the logs to eval_res_dali_load_only in the current working directory.

Profiling

The demos/streampetr/tools/run_dali_profiling.sh script captures Nsight Systems profiles for the PyTorch reference and DALI Pipeline Framework data loaders on eight GPUs. It uses the configurations under Profiling/ with the same 1024 × 372 image workload and replicated sampling as the training comparison, shortened to 100 iterations with NVTX ranges enabled.

Run it inside the prepared demo container, with the dataset available and the Nsight Systems nsys command on PATH:

cd /streampetr/tools
bash run_dali_profiling.sh

The profiling script calls dist_train.sh with --profile to enable Nsight Systems capture. The optional --profile-output PREFIX argument selects the report prefix; its default is profile_output. The helper parses these options itself and uses the prefix for the nsys profile --output option. Capture uses the CUDA profiler API start/stop calls in the training code. Validation remains disabled, as for other runs launched through dist_train.sh.

The script writes reports to the current working directory with the prefixes original_profile and dali_profile, and stdout/stderr logs under profiling_res/. Open the reports in Nsight Systems to inspect the NVTX ranges. See the profiling guide for details of the instrumentation.
